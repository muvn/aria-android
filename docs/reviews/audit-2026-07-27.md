# Aria Android Mobile Security Audit

**Date:** 2026-07-27
**Scope:** `aria-android` (Kotlin app + UniFFI/Rust glue in `aria-mobile-core`)
**App:** `com.solutions5060.aria` — SIP softphone (stores SIP creds, QR provisioning, FCM VoIP push)
**Reviewer:** Automated security audit (read-only, no fixes applied)

---

## Executive Summary

The app is functionally a VoIP softphone that stores long-lived SIP credentials and PBX auth tokens and receives VoIP push. The dominant risk is **credential-at-rest handling**: SIP passwords, the extension JWT, and the gateway token are all persisted in **plaintext `SharedPreferences`**, and the manifest sets **`allowBackup="true"`**, so those secrets flow into Android backups where they can be extracted off-device. Several code paths also **write secrets to logcat** (the full provisioning URI containing the base64-encoded SIP password, the raw FCM data payload including the call token, and a prefix of the gateway token). There is **no ProGuard/log stripping** configured, so this logging ships in release builds.

Secondary issues: the QR provisioning payload is **not validated against any trusted host allowlist**, so a hostile QR can silently point the client at an attacker-controlled SIP server and API endpoint; the exported `MainActivity` accepts a `call_token` intent extra from any app (intent injection into the call-accept path); and there is no `network_security_config`, with SIP defaulting to cleartext `udp`.

On the positive side: the Rust `reqwest` HTTP client uses **default certificate validation** (no trust-all / no disabled hostname verification found), the gateway defaults to `https`, cleartext HTTP is blocked by the platform default (targetSdk 36, no opt-in), `AriaFirebaseMessagingService` and `IncomingCallService` are correctly `exported="false"`, and `AriaConnectionService` is guarded by the system `BIND_TELECOM_CONNECTION_SERVICE` permission.

## CRITICAL

### C1. SIP password, JWT, and gateway token stored in plaintext SharedPreferences

**Files:**
- `app/src/main/kotlin/com/solutions5060/aria/ui/AriaApp.kt:135` (`putString(KEY_SIP_PASSWORD, creds.password)`), `:242-247` (`jwt`, `gateway_token`)
- `app/src/main/kotlin/com/solutions5060/aria/ui/settings/SettingsScreen.kt:182` (`putString("sip_password", creds.password)`), `:110-127` (`jwt`, `gateway_token`)

```kotlin
prefs.edit()
    .putString(KEY_SIP_USERNAME, creds.username)
    .putString(KEY_SIP_PASSWORD, creds.password)   // plaintext
    ...
```

```kotlin
prefs.edit()
    .putString("jwt", loginResult.jwt)             // plaintext bearer token
    .putString("gateway_token", gwToken)           // plaintext
    .apply()
```

`getSharedPreferences(PREFS_NAME, Context.MODE_PRIVATE)` writes an unencrypted XML file at `/data/data/com.solutions5060.aria/shared_prefs/aria_prefs.xml`. The SIP password grants full account takeover (place/receive calls, toll fraud), and the JWT / gateway token authorize the PBX and push gateway APIs.

**Failure scenario:** On a rooted device, a device with a custom recovery, a lost/stolen unlocked device, or via any backup extraction path (see H1), the file is readable and every secret is recovered verbatim. There is no OS-level encryption beyond full-disk/file-based encryption, which is bypassed once the device is unlocked or backed up.

**Fix:** Store all secrets (SIP password, `jwt`, `gateway_token`, and ideally the auth-bearing IDs) using `EncryptedSharedPreferences` with an `AndroidKeyStore`-backed `MasterKey` (`AES256_GCM`), or the Jetpack Security / DataStore encrypted equivalent. Keep non-secret config (username, domain, transport) in normal prefs if desired, but never the password or tokens.

## HIGH

### H1. `allowBackup="true"` exfiltrates the plaintext credentials off-device

**File:** `app/src/main/AndroidManifest.xml:27`

```xml
<application
    android:name=".AriaApplication"
    android:allowBackup="true"
    ...
```

With `allowBackup="true"` (and no `fullBackupContent` / `dataExtractionRules` exclusion), Android Auto Backup copies the app's `shared_prefs` — including the plaintext `aria_prefs.xml` from C1 — into Google cloud backups and makes them retrievable via `adb backup` on debug-capable / developer devices. Combined with C1, this turns local plaintext storage into a remote/offline credential-exfiltration channel.

**Failure scenario:** An attacker with transient ADB access (developer options enabled, or an evil-maid scenario) runs `adb backup -f out.ab com.solutions5060.aria`, unpacks the archive, and reads `sip_password`, `jwt`, and `gateway_token` in cleartext — no root required.

**Fix:** Set `android:allowBackup="false"`, or at minimum provide `android:dataExtractionRules` / `android:fullBackupContent` XML that excludes the `aria_prefs` file. Fixing C1 (encrypted storage) also mitigates this, but disabling backup of the secrets is defense-in-depth.

### H2. Secrets written to logcat (provisioning URI w/ password, FCM payload, gateway token)

**Files:**
- `app/src/main/kotlin/com/solutions5060/aria/ui/settings/QRScannerScreen.kt:52` — `Log.d(TAG, "Parsing provisioning URI: $uriString")` and `:67` logs server/user/api/tenant
- `app/src/main/kotlin/com/solutions5060/aria/service/AriaFirebaseMessagingService.kt:45` — `Log.i(TAG, "FCM message received: ${message.data}")`
- `app/src/main/kotlin/com/solutions5060/aria/ui/AriaApp.kt:249` — `Log.d(TAG, "Full login completed, gwUrl=$gwUrl, gwToken=${gwToken.take(20)}...")`

```kotlin
// QRScannerScreen.kt:52 — the URI contains ?pass=<base64 SIP password>
Log.d(TAG, "Parsing provisioning URI: $uriString")
```

```kotlin
// AriaFirebaseMessagingService.kt:45 — logs full call_token used to answer the call
Log.i(TAG, "FCM message received: ${message.data}")
```

The provisioning URI embeds the SIP password as a `pass=` base64 query parameter, so line 52 logs the credential (trivially base64-decoded). The FCM `data` map contains the `callToken` that authorizes answering the inbound call at the gateway. `app/build.gradle.kts` enables `isMinifyEnabled = true` but `proguard-rules.pro` is empty — there is **no log-stripping rule**, so all of this logging is present in release builds. Any app holding `READ_LOGS` (or anyone with ADB / a crash-reporting SDK) can harvest these.

**Fix:** Remove or gate all logging of credential-bearing values behind `BuildConfig.DEBUG`, and never log the raw provisioning URI, the FCM `data` map, or any token prefix. Add ProGuard rules to strip `Log.d`/`Log.v` in release. Redact the `pass` parameter before logging the URI.

## MEDIUM

### M1. QR provisioning payload is not validated against a trusted host allowlist

**File:** `app/src/main/kotlin/com/solutions5060/aria/ui/settings/QRScannerScreen.kt:50-84`

```kotlin
if (uri.scheme != "aria" || uri.host != "provision") return null
val server = uri.getQueryParameter("server") ?: return null
...
val apiUrl = uri.getQueryParameter("api") ?: ""
```

Beyond the fixed `aria://provision` scheme check, no field is validated: `server`, `api`, `tenant`, and `port` are accepted verbatim. The scanned `apiUrl` is then used to POST the extension login (`extensionLogin(username, password, ...)` in `SettingsScreen.kt:98-104` and `AriaApp.kt:232-233`), and `server` becomes the SIP registrar the device authenticates to.

**Failure scenario:** A user is socially engineered into scanning a malicious "Aria" QR (e.g. a poster, email, or spoofed admin panel). The QR sets `api=https://attacker.example` and `server=attacker-sip`, so the app sends the provisioned SIP credentials to the attacker's API and registers the phone to the attacker's SIP server — enabling call interception/MITM and credential capture. There is also no `https` enforcement on `api`.

**Fix:** Validate `apiUrl`/`server` against an allowlist of trusted domains (e.g. `*.ariaroute.com`), require `https` for `apiUrl`, reject non-numeric/out-of-range ports, and show the user the target server/domain for explicit confirmation before storing and logging in. Consider signing the provisioning payload and verifying the signature in-app.

### M2. Exported MainActivity accepts `call_token` intent extra → intent injection into call-accept path

**Files:** `app/src/main/AndroidManifest.xml:34-52` (activity `exported="true"`), `app/src/main/kotlin/com/solutions5060/aria/MainActivity.kt:48-61`

```kotlin
private fun handleIncomingCallIntent(intent: Intent?) {
    val callToken = intent?.getStringExtra(IncomingCallService.EXTRA_CALL_TOKEN) ?: return
    ...
    incomingCallToken.value = callToken   // AriaApp then calls engine.acceptIncomingCall(token)
```

`MainActivity` is exported (it must be, for the launcher and `tel:`/`sip:` filters), and `handleIncomingCallIntent` reads a `call_token` string extra from *any* incoming intent, not just the internal `PendingIntent` from `IncomingCallService`. `AriaApp.kt:181-194` then feeds that token straight into `engine.acceptIncomingCall(token, ...)`.

**Failure scenario:** A malicious app on the device sends `Intent(component=MainActivity).putExtra("call_token", <value>)`. This drives the app's answer flow with an attacker-supplied token — at minimum a UI-spoof / unexpected-state nuisance, and a potential call-hijack primitive if the token space is guessable. The `tel:`/`sip:` `DIAL` filter similarly lets any app pre-fill dial targets.

**Fix:** Do not trust call-control extras from arbitrary intents. Deliver the token only via an explicit-component `PendingIntent` and verify provenance (e.g. a per-launch nonce set by `IncomingCallService`, or verify the sender), or route accept/reject exclusively through the permission-guarded `AriaConnectionService` rather than an exported activity extra.

### M3. No `network_security_config`; SIP defaults to cleartext `udp`

**Files:** `app/src/main/kotlin/com/solutions5060/aria/ui/settings/SettingsScreen.kt:54` (`sip_transport` default `"udp"`), no `res/xml/network_security_config.xml` present

```kotlin
var sipTransport by rememberSaveable { mutableStateOf(prefs.getString("sip_transport", "udp") ?: "udp") }
```

The HTTP/API path is protected (platform blocks cleartext for targetSdk 36 and the Rust client uses default TLS), but SIP signaling defaults to `udp` and the provisioning payload defaults `transport` to `"udp"` (`QRScannerScreen.kt:62`). SIP over UDP/TCP carries call metadata (who calls whom) in cleartext, and media (RTP) is unencrypted, on the native socket path which is not covered by `network_security_config` anyway.

**Failure scenario:** On a hostile Wi-Fi network, an on-path attacker observes SIP signaling (call metadata, headers) and can capture/inject RTP audio. Digest auth protects the password itself, but not confidentiality of calls.

**Fix:** Prefer/enforce `tls` transport for SIP (and SRTP for media) in provisioning defaults; add a `network_security_config.xml` that disables cleartext (`cleartextTrafficPermitted="false"`) as defense-in-depth and to document intent. Reject `udp`/`tcp` provisioning unless explicitly overridden.

### M4. Auth tokens/IDs copied to the system clipboard

**File:** `app/src/main/kotlin/com/solutions5060/aria/ui/settings/SettingsScreen.kt:624`

```kotlin
clipboard.setText(AnnotatedString(value))
Toast.makeText(context, "Copied to clipboard", Toast.LENGTH_SHORT).show()
```

Device ID / Extension ID are copyable. These are lower sensitivity than the password/JWT, but the global clipboard is readable by other apps (pre-Android 12) and surfaces in clipboard history. If this pattern is extended to tokens it becomes a leak.

**Fix:** Avoid clipboard for any secret; if unavoidable, flag the clip as sensitive (`ClipDescription.EXTRA_IS_SENSITIVE`) and clear it after a timeout.

## LOW

### L1. Firebase API key committed in `app/google-services.json`

**File:** `app/google-services.json` (`current_key: AIzaSyALcPG5K_dMNLcq7AYIqZOYiATk_hw-080`)

This is expected for FCM and is not a private secret (it identifies the Firebase project and is restricted by package name + SHA). Informational: ensure the key is API-restricted in the Google Cloud console (FCM only, package/SHA allowlist) so it can't be abused for other Google APIs.

### L2. Empty ProGuard/R8 config despite `isMinifyEnabled = true`

**Files:** `app/build.gradle.kts:20-28`, empty `app/proguard-rules.pro`

No custom keep/strip rules. Beyond the log-stripping gap noted in H2, verify UniFFI/JNA classes survive R8 (they rely on reflection/native bindings). Add explicit keep rules and a release log-strip rule.

### L3. `MainActivity` shows on lock screen (`showOnLockScreen`, `turnScreenOn`)

**File:** `app/src/main/AndroidManifest.xml:38-39`

Necessary for incoming-call UX, but the app has no `FLAG_SECURE` on screens that render account details / IDs, so call and settings content is screenshot-able and visible over the lock screen. Consider `FLAG_SECURE` on the call and settings surfaces.

## Positive observations (no action required)

- Rust `reqwest::Client::builder()` (`aria-mobile-core/src/gateway_client.rs:93`) uses default certificate and hostname validation — no `danger_accept_invalid_certs`, no custom trust-all `TrustManager`, no disabled `HostnameVerifier` found anywhere in Kotlin or Rust.
- Gateway defaults to `https://push.ariaroute.com`; TLS branch chosen for `https` scheme (`gateway_client.rs:163-171`).
- `AriaFirebaseMessagingService` and `IncomingCallService` are `exported="false"`; `AriaConnectionService` is guarded by `android.permission.BIND_TELECOM_CONNECTION_SERVICE`.
- All `PendingIntent`s use `FLAG_IMMUTABLE`.
- `android:debuggable` is not set (defaults to false in release).
- No cleartext `http://` endpoints in app source; platform default blocks cleartext HTTP at targetSdk 36.
